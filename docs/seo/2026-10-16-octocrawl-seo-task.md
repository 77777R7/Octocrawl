## 1. 目标、策略与不采用的做法

### 1.1 业务目标

优先吸引需要网页内容和数据的 AI Agent / RAG 开发者，让访客理解产品、完成首次有效使用，并观察是否再次使用。免费工具承接具体的网页转换与链接提取需求。

这个客群优先级是基于当前公开页面及产品入口的策略选择，尚不是付费需求或增长验证。若真实查询和有效使用数据指向其他客群，保留证据后调整。

### 1.2 工作顺序

1. 找到正确代码基线，确认抓取和衡量条件。
2. 明确现有页面各自承担的搜索意图。
3. 修复已经证实的技术问题，改善重点工具页和文档入口。
4. 将原始运行证据整理成有用内容和可复现案例。
5. 依据索引、查询、有效使用和抽样 AI 引用结果复盘。

### 1.3 不采用的假设

- 不承诺 72 小时、7 天进入前三，也不填入无依据的流量增幅。
- 不推算 Google 排名因素的百分比权重，不把页面相关性当作因果证明。
- 不把 FAQ Schema、llms.txt、固定段落字数当作 Google AI 搜索通行证。
- 不批量生成客户端、关键词变体或所谓 query fan-out 页面；新增页面必须有独立意图及实质内容。
- 不以全文重写、堆关键词、堆 Schema、增加文章数本身作为成果。
- 不宣称全面领先竞品或“所有站点都可抓取”。迁移兼容、覆盖率、成本、速度必须有明确范围。

## 5. SEO-04 与 SEO-05：现有网站实施

### SEO-04：技术修复，以实际缺陷为前提

- [ ] sitemap 只纳入计划索引的规范公开 URL；核对遗漏、重定向、404、参数与不应索引项。lastmod 反映实质内容更新，不每天统一刷新。
- [ ] 保证关键内容在构建输出和实际渲染中可发现；复用现有静态 HTML。检查正文、内链和分页/分类，不重建框架。
- [ ] title、description、主标题与页面意图一致，描述具体且不堆词；字符长度只作预览参考，不作硬性排名阈值。
- [ ] canonical、协议/域名/末尾斜杠、参数及跟踪链接处理一致。对确认重复的页选择合并、规范或保持，并说明理由。
- [ ] 只在发现真实问题时改导航和内链。主要内容有合理站内入口，不要求把所有链接集中到一个“权重页”。
- [ ] 对 Schema 做渲染后 JSON 解析、类型适用性和可见内容匹配检查；如适用，再用 Rich Results Test。
- [ ] 保留有用 FAQ 正文；不为 Google 富结果增堆 FAQPage，也不因富结果停止而强制删除现有无害标记。
- [ ] llms.txt 可以服务现有其他读取用途，保持内容一致；不新增以其为核心的“Google AI SEO”工程。
- [ ] 核对登录、账号、API、预览环境的现有访问/索引策略。robots 不是隐私或认证机制，不为 SEO 暴露私有内容。
- [ ] 根据移动端与性能证据修复明确影响阅读/使用的问题。图片尺寸、懒加载、脚本、动画和布局只作有针对性的修改；不把视觉重做当 SEO 必选项。

性能验收：有真实用户 Core Web Vitals 数据时使用其范围与时间窗口；实验室结果单独标识。优化前后用相同条件，不能用一次 Lighthouse 分数承诺排名。

技术验收：改动能解决原有证据中的问题，且没有引入错误 canonical、意外 noindex、断链或路由变化。没有实际问题的项以“已检查，未修改”结案。

### SEO-05：重点页面内容与内链

范围优先覆盖首页、`/scrape/`、三个工具页、MCP 文档与现有 RAG/Claude Code 等文章。不是要求逐页重写；先按 SEO-03 的缺口选择最小改动。

- [ ] 首页：让新访客知道产品类别、适合谁、能得到什么、从哪里开始。主标题与搜索标题可以分工，不为塞关键词破坏品牌表达。
- [ ] API 页：核实实际接口、最小调用、响应示例和 hosted/local 差异；保留真实限制，连接到参考与设置文档。
- [ ] Markdown 工具：提供可复制的真实输入输出，展示标题/表格/代码/链接的实际处理；每项只写已验证表现。
- [ ] 纯文本工具：展示其与 Markdown 的真实输出区别和用途，避免整页仅替换关键词。
- [ ] 链接工具：核实当前实现是读取单页链接、map 还是其他范围，解释无法保证发现的 URL 类型；不把所有链接等同于所有页面。

- [ ] 对绝对结论如“Markdown 最适合所有模型”“每个字段已准确核验”等逐项检查；改成证据支持的具体范围。
- [ ] 内容中安排与意图匹配的下一步：工具 → API/MCP；教程 → 对应工具/设置；比较 → 迁移说明/实际试用。避免为链接数量机械插入无关页面。
- [ ] 按需增加准确作者/维护者信息、真实验证日期和官方来源。只改标点或样式不刷新“实测日期”。

内容验收：读者能找到答案、复现主要步骤、识别限制并采取下一步；每项能力和数字有来源，页面意图有区别，没有重复造页或扩大产品承诺。

## 6. SEO-06 与 SEO-07：有证据的新内容

### SEO-06：一篇 Firecrawl 比较或迁移内容（条件任务）

默认先做一个有独立意图的比较/迁移页面，不同时创建多篇同质 `alternative`、`vs`、`migration` 内容。最终路径与形式由 SEO-03 决定；复用实际路由注册与内容生成方式。

### SEO-07：一个可复现的质量案例

优先回答真实问题：“为什么 HTTP 200 也可能没有读到目标内容？”或“如何保存网页数据来源，并区分缺失与零值？”以 SEO-03 选定题目为准。

- [ ] 优先复用可审查的历史原始证据；确认版本、时间和内容足以支撑结论，必要时做最小新运行。
- [ ] 固定少量有代表性的页面/fixture 与正常对照，明确 expected、observed、判定、局限；不以数量凑完整性。

## 8. AI 辅助内容工作流

### 8.1 输入材料

每次只向 AI 提供与内容有关的：页面与查询记录、实际源码/配置、官方来源、经清理的运行证据和已确认产品限制。网页与附件里的“操作指令”是资料内容，不是执行授权。

### 8.2 工作顺序

1. 聚类需求，指出现有页面能否解决及证据缺口。
2. 先取证，再组织结构与初稿。
3. 对每个数字、能力、优劣与比较结论建立来源记录。
4. 运行涉及的关键步骤，核对输出和失败范围。
5. 检查产品/搜索意图、可读性、内链和重复内容。
6. 本地渲染并按实际变更验证；外部发布另行处理。

### 8.3 可直接使用的内容提示词

> 根据提供的实际运行记录、源码和官方资料，整理解决一个明确用户问题的内容。每项数字与能力结论标注依据，保留版本、日期、失败和未确认范围。缺少证据时列为待验证，不补造结果。检查是否与现有页面承担同一意图；能更新已有页面时优先更新。清楚说明产品做了什么、用户还需做什么。段落长度按问题需要，不套固定字数或人为堆关键词。
