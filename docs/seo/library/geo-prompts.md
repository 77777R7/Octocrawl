# GEO 观测题库（Octocrawl）

状态：v0.0.1，2026-10-27 起草，**未经 Howard 批准**，还没有被任何 AI 助手问过。共 124 条 prompt，10 个一级主题。
用途：一批固定的问题，每周拿去问各个 AI 助手，看它会不会自然地提到 Octocrawl、说得对不对、引用了谁。怎么问、怎么记、怎么算、怎么复查，见 [geo-protocol.md](geo-protocol.md)。
来源与方法：[GEO 研究记录](../../../research/seo/2026-10-27-geo-research.md) §7 与 §9。这份题库的入库思路借自一份外部题库的方法页；入库标准的表述和全部题目都从我们自己的证据另写，没有搬用对方的任何一条。

## 入库标准（四条都要过）

1. **有人真的这样问。**每条都带来源：Search Console 的真实查询、Hacker News 与 GitHub 的真实条目、Google 与 Bing 的自动补全、SERP 簇。不能因为我们想得出这个问题就收录；证据不够的主题不写，放进文末「没写的」。
2. **跟 Octocrawl 的能力有关。**要么说得出它负责哪一步，要么明确它不该参与（范围外对照题）。
3. **答案能看出东西。**中立提问下，能看出助手是否自然推荐、能力边界说得对不对、有没有编造。
4. **能落到具体页面。**每条对应框架里的一个页面或一类内容（「页面对应」列），而不是只产出一个提及次数。

## 怎么读这张表

- **应提及**：这个 prompt 里的任务，Octocrawl **现在就能完成**，才标「应提及」。「视条件」指只在某种模式下能做（本地、需账号）或只能做一部分。「不应提及」是校准用的对照题：看助手会不会夸大。能力边界以仓库里的 `README.md`、`docs/hosted-api.md`、`docs/access.md`、`docs/local-setup.md`、`docs/monitors.md` 与 ROADMAP 为准（2026-10-27 的整理稿在 `.w2l/seo/2026-10-27/capability-boundary.md`，git 忽略）；产品能力变了，要回来复审这一列。
- **模式**：hosted 无 key 即可（只有 `scrape` 和 `map`）；hosted 需账号（crawl、batch、浏览器通道）；仅本地（登录态、Monitor、页面操作、`installed_chrome`）；「—」表示不该提及。
- **来源**：`GSC` 是真实查询；`HN` 是 Hacker News 条目号；`GH` 是 GitHub issue；`补全` 是 Google 或 Bing 的自动补全原文（Google 会把输入原样回显，所以补全只说明有人在输入这类短语，不说明量）；`SERP` 是该关键词的搜索结果簇；`框架` 是 [核心框架](../core-seo-framework.md) 的关键词簇。
- **页面对应**：这个 prompt 的答案应该由哪类页面承接（对比页暂停，见框架 §4.2）。
- prompt 里**绝不出现** Octocrawl 这个名字。往 prompt 里加品牌名来抬高提及率是被禁止的（协议第 5 节第 1 条）。

## 构成与证据强弱

- **核心集**：标 ● 的 28 条（应提及 14、视条件 8、不应提及 6），是协议里每周要问的那一批；其余每月问或接入工具后再问。挑选标准：应提及的覆盖最主要的选型与操作场景，视条件的覆盖本地与账号两类限制，不应提及的覆盖最容易被夸大的几类。
- 类型：选型 41、操作 29、排障 23、评测 19、概念 12。
- 应提及 27、视条件 70、不应提及 27。「视条件」占多数，因为 hosted 与 local 的能力不同。
- 来源条数：Hacker News 85、自动补全 82、GitHub 59、SERP 簇 34、Search Console 29、框架 18、ai-visibility 15（一条 prompt 可有多个来源）。
- **Reddit 贡献为零**：这台机器读不到（见 [data-sources.md](data-sources.md)）。
- **Search Console 只支撑很少几条**：它的真实查询几乎全是同一类（find all pages of a website），而且大多展示极少。需求强弱不能从条数推断。
- HN 与 GitHub 条目是真实讨论，但互动量低；「有人问过」不等于「很多人问」。
- 来源引用已全部回查：322 条出处在证据文件里都存在（研究记录 §9）。

## 维护规则

- 新增或修改一条，必须写来源，且来源必须能回到证据文件；回查方法见研究记录 §9。
- 产品能力变化（例如 hosted 上线 Monitor、新增能力、暂停项解除）后，回来复审「应提及」「模式」「核对要点」三列，并在 [decisions.md](decisions.md) 记一行。
- 不删旧版本的结论：改动写进版本日志，旧版本留在 git 历史里。
- 不要为了让某条 prompt「提及率」好看而改它。提及率低说明缺内容或产品做不了，按协议第 5 节处理。
