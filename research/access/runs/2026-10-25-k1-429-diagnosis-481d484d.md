## What every 429 had in common

- The arms with compatible_transport (enhanced, control, combined) asked T007 and T018 through `http_compat` (impit) first, and it read both; the 429s on those two are from the arms without it.
- Every one came from Octocrawl's own exit (Clash, `127.0.0.1:7890`; exits 103.142.140.x).
- None carried `Retry-After`. The 429's `retryAt` was always the HTTP subject's 250 ms default (`host_cooldown_set` with `cooldownMs: 250`).
- F4's shadow (`ladder_action_decision`, where recorded) said `wait_retry_after` (reason `retry_after`) on every one; the ladder's actual action was `stop`.
- The ladder stopped at the rung that got the 429, almost always `http`: `channelsTried: ["http"]`. No browser rung ran. That held even for T018, whose 429 the gate already called `captcha` (PerimeterX): `LadderRunner` ended the run on any result with `retryAt`, whatever the block.
- Each task's host appears in no other task of the set, so no same-host task ran just before. Across K1's arms the same host was asked about once every 3–15 minutes (for T042 in window 1: 12:51:50, 12:56:13, 13:01:03, 13:04:03 UTC). robots.txt names no crawl-delay for `*` on any of these hosts (realtor.com's `Crawl-delay: 1` is for bingbot only).
- The first request of the day to each of the three frozen hosts, from curl on 2026-10-25 06:57 UTC, already got 429 (below). Pacing was not the cause.

## What was ours, and the fix (`481d484d`)

Two defects, both in Octocrawl:

1. `classifyGate` (packages/http-core/src/gate.ts) called every 429 a rate limit unless its body held PerimeterX's challenge. It now reads three headers on a 429: `x-vercel-mitigated: challenge` and a non-empty `x-kpsdk-ct` name a JS challenge (`bot_detected_generic`); `x-page-id: wildcard-challenge-handler` names Expedia's captcha (`captcha`). Any other 429 stays `rate_limit`.
2. `LadderRunner` (packages/bench/src/routing/ladder.ts) ended the run on any result with `retryAt`. It now ends it there only for a rate limit, a result that is not a block, or a deferred retry. After a challenge served with 429 or 503 it goes on to the next local rungs, which share the origin's cooldown with the http rung (`OriginScheduler`), so any Retry-After is still waited. It skips vendor rungs, and says so in a `ladder_channel_skipped` event: after a 429 the run keeps its own exit (ADR 0005).

Tests written first and seen failing: `packages/http-core/test/gate.test.ts` (the three headers, and three that must stay `rate_limit`) and `packages/bench/test/ladder.test.ts` (climbing past a challenge 429 to `browser_local`, for `bot_detected_generic` and `captcha`; stopping when only vendor rungs are left).

## Not ours: T042 (Kasada), T078, T008

- T042: Kasada refused the bundled Chromium and the installed Chrome alike on the Clash exit, after the fix. Firecrawl's basic mode read it on both K1 days. Options, none built: (a) let a challenge served with 429 move on to a vendor rung (Steel), which ADR 0005 now keeps off after a 429 — Howard's call whether a vendor's challenge sent with 429 counts as "a 429" for that rule; (b) try the page through the user's own residential exit (`egress_sessions`, Webshare) from the start of the run, not as a switch; (c) record it as a frozen-task loss to Kasada on datacenter exits.
- T078: Instagram's empty 429 is not isolated from a login wall; a run from another exit would tell them apart. Firecrawl does not serve the site.
- T008: GitHub's abuse detection on a shared exit. Nothing in the run's pacing explains it (one request per arm, minutes apart).

## Found on the way (not changed)

- F4's shadow `decideNext` (packages/bench/src/routing/decideNext.ts) says `wait_retry_after` for every 429, the challenge ones too; after the fix the ladder's actual action on them is `next_rung`, and the live run shows that was the action that worked.
- ironmountain.com's robots.txt sits behind the same Vercel challenge (429). The engine records it as `no_robots` and goes on; whether a robots.txt answered with 429 should count as unreachable is a question for the robots owners.
