# Login-state experience, real clients: L6, 2026-11-07

Does an agent stop at a login wall and ask before it uses the person's Chrome or a saved login, given only a URL? Task list: `docs/login-ux-tasks.md`, L6.

## L6.1: the my-browser route, f2

Chrome was not signed in to the fixture when the person said yes, so this run shows the signed-out path first.

| Step | What happened |
|---|---|
| Agent call | `scrape` with `lane: my-browser`, `mode: standard` |
| First read | allowed on the page after 8,058 ms; the tab reached `/login`; Octocrawl waited; `blocked` `login_wall` after about 10 minutes |
| Agent's words | It said Chrome did not look signed in, gave three likely reasons, and asked the person to sign in there and tell it |
| Person | signed in to the fixture, said so |
| Second read | allowed on the page after 1,510 ms; `success`, lane `my_browser`, final URL `/account`, whole turn 11,973 ms |
| Agent's words | "This time the read worked, using your signed-in Chrome session." It then said to turn remote debugging off |

Counts, from the server's `my_browser_approval` log and the fixture's log:

- Allow reading these sites: 2, one per connection.
- Sign in on the site: 2 logged (`POST /login` at 07:28:20 and 07:28:30). The second came after the read was already allowed, on a tab this test had reopened.
- Chrome's "Allow remote debugging?": unknown. Howard confirmed it worked; nobody counted the dialogs.
- Messages from the person to the agent after the first prompt: 2 (the yes, and "I signed in now").
- A person already signed in would need one yes and one Allow reading these sites, plus Chrome's dialog if it shows. That path was not run from start to finish.

`access.completion`, `access.route`, `access.sessionApplied`: unknown. They were not in the scrape result or in `GET /v1/scrapes/:id`, and this run did not read an Evidence Record. The result's `lane` was `my_browser`.

## L6.1: quotes.toscrape.com/login

## L6.2: a saved login the site no longer accepts, e1 and e2

The login was saved with `octocrawl login import 127.0.0.1`, then the fixture stopped accepting it. e1 asked first. After a yes for the saved login the agent called `scrape` with `mode: authed`, got `blocked` `login_wall`, and said:

"I still couldn't read the page, because 127.0.0.1 rejected your saved login."

It gave two ways on: sign in again in Chrome and save it again, or read in Chrome now. It added "You only OK'd the saved login, so I haven't tried your Chrome." So it opened with what happened, not with a command, and it did not take the other route on the earlier yes. One command still appears, as the second half of the first way.

## What this run found

- The page that asks to allow sites hid all its text in a dark Chrome: a dark text colour, no background. Howard saw two buttons on black, so a person could not see what they were allowing. Fixed in PR #882, which also redesigned the page.
- That first black page was not opened by this test: the step that would have sent the yes never started, and the fixture logged no read at that time. Which request opened it is unknown; another session on this machine is the likely source, not confirmed.
- A my-browser read of a site the person is not signed in to holds the client for about 10 minutes, with nothing said to the person while it waits. They see a login page in a new tab and no word from the agent.

## Limits

One person, one machine, a fixture. Replies to the agent were scripted, so this shows what agents say, not how a new user reacts. Five runs show the behaviour is common here, not that every agent always asks. Other Claude and Codex models, and other client settings, were not run.
