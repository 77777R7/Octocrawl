# Login UX A3 in a real Chrome, 2026-11-08

Does a my-browser batch read on when the person's Chrome quits in the middle of it and comes back? Task list: `docs/login-ux-tasks.md`, A3.

## Setup

- Source commit: `7852303b` (branch `claude/login-ux-a3-chrome-resume`, PR #901, on top of A2 #897 and A1 #896; none on main yet). Rounds 1 to 4 ran it as committed. Round 5 ran it with the fix this record's commit adds, as uncommitted changes, with two differences made after it: round 5 logged `chrome_refused` at every refusal, where the commit logs the first only; and in round 5 each refused connection left its cancel listener on the batch's signal until the batch ended (48 here), which the commit removes. `npx tsc --build` ran before each server start.
- Server: `W2L_SESSIONS_FILE=<scratch>/sessions.json node --import <scratch>/wslog.mjs packages/cli/dist/cli.js serve --port 8793 --task-root <scratch>/tasks`, loopback, no remembered sites at the start. Restarted once, before round 5, to load the fix.
- Network: `HTTPS_PROXY`/`HTTP_PROXY` unset for the server and the client (direct). Chrome loaded the pages itself; Octocrawl fetched nothing.
- Chrome: Howard's own Google Chrome 156, default profile, remote debugging on through `chrome://inspect`, port 9222. Howard sat at Chrome and clicked and counted Chrome's "Allow remote debugging?" dialogs.
- Fixture: a throwaway local site on `127.0.0.1:8796`, not in the repository, that answers every page after 4 s, so a page is still loading when Chrome goes.
- Requests: one `POST /v1/batches` per round with `lane: "my-browser"`, the job polled every 0.5 s, from a scratch script.
- Measured by the session: the server's `my_browser_approval` log, every WebSocket the server opened (a `--import` preload logging `new WebSocket`, open, error and close), every non-Chrome TCP connection to port 9222 and Chrome's listening ports sampled about every 0.1 s with `lsof`, the fixture's request log, the batch's `results.jsonl`. Measured by Howard: Chrome's dialogs.

- 14:28:45.29 Chrome (pid 60683) sent SIGTERM; gone by 14:28:45.52. The connection closed at 14:28:45.44 (WebSocket error, close 1006); the batch logged `chrome_lost` and said `waitingForApproval: true`.

### Round 5, with the fix

The fix: a connection Chrome refuses within 1 s, after it came back, is asked for again a second later, until the 10-minute wait is up; one refused after 1 s or more is taken as the person declining Chrome's Allow and stands. Tests: `packages/api/test/myBrowser.test.ts`, "connects again when Chrome refuses the first connections at once…" (failed on `7852303b` with the round-4 result, passes with the fix) and "does not connect again when Chrome refused a connection after a while…".

## What this run shows

- A3 reads on after Chrome goes and comes back: with the fix, the page being read when Chrome went was read again, and the 35 after it were read, with no page of Octocrawl's asking again and one Chrome dialog.
- Before the fix it did not: a Chrome just started refused the first connection at once, and that refusal ended every page left.
- Remote debugging turned on in `chrome://inspect` stayed on across both Chrome restarts here: port 9222 listened within a second of the new Chrome starting, with no step by Howard.
- Whether the waiting check (a TCP connection that sends nothing) can draw a dialog is not settled here: while Chrome was gone nothing listened, and the check that found the new Chrome was followed at once by a WebSocket. Howard counted one dialog in all after Chrome came back.

## Not explained

- Why Chrome refused connections at once for 48 s in round 5 and then took one that took 2.2 s to open. One reading: Chrome refused until the person did something in the new window (a restore prompt, the dialog itself), and the 49th connection waited for his Allow; another: Chrome was still starting. Not measured: Howard's view of the 48 s was not recorded, only the one dialog.
- Whether each refused connection showed and withdrew a dialog: Howard counted one, so not visibly.

## Limits

One person, one machine, one Chrome profile, a local fixture, no site behind a login. Chrome went by SIGTERM, not Cmd-Q: Chrome cancelled the AppleScript quit in round 3 (a confirmation it showed, presumably; not seen by the session), and in rounds 1 and 2 the batch ended before Howard quit Chrome. Cmd-Q closes tabs before the connection, which the fake-Chrome test "reads on as well when Chrome closes its tabs a moment before the connection" covers and this run did not. Chrome came back after 19 s and 27 s; the 10-minute limit was not reached here. Chrome's dialogs were counted by Howard, not timed.
