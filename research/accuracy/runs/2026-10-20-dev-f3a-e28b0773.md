## What run 1 showed

H01 is RFC 9110 (source 1,187,554 bytes). The HTTP lane's main content is the ABNF appendix, and the case's identity check (`markdownIncludes "RFC 9110"`) fails on it. In run 1 the candidates ran: the whole-document candidate is not read above `MAX_TASK_SELECTION_HTML` (1,000,000 characters), which this source exceeds, so it was left out by the limit (this follows from the code and the source size; the SDK response carries no trace to show it); the declared-data candidate wrote the page's `<title>` ("RFC 9110: HTTP Semantics") under the appendix, which passed the check. The delivered page was still the appendix: a false success. Commit `e28b0773` leaves the page title out of the declared-data candidate (a title names the page, not its content), with a negative fixture in `packages/bench/test/candidateExtraction.test.ts`. The page has no citation tags or JSON-LD, so in run 2 no candidate passed and the main content stayed.

## What this does and does not show

No regression on the development or regression set after the fix. The F3a gain the plan expects on H01 (the RFC header through the document candidate) does not happen here, because the capture is over the whole-document limit; H07 (WCAG) fails on fields, not on its identity check, so no candidate runs there. F3a's own evidence is the fixtures in `packages/bench/test/candidateExtraction.test.ts` (the HTTP lane through `ResilientHttpSubject` included) and the page-cache case in `packages/api/test/pageCache.test.ts`.
