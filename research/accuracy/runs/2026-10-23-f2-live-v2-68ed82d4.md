## How a live page is scored, and page drift

This follows K1 window 1's "How a live page is scored" ([2026-10-21-k1-w1-live-v2-322de68e.md](2026-10-21-k1-w1-live-v2-322de68e.md)) unchanged:
- `sameSource` is dropped, because a live page never has the sealed capture's `rawSha256`.
- Every other check is kept under the scorer's own rule. Unit, date and period are not scored where the gold leaves them unknown.
- **Accepted:** every required field is correct, with no duplicates and nothing fabricated.
- **False success:** the answer claimed success and was not accepted. For Octocrawl, a claim is status `success` with a verify that did not fail. Firecrawl is sent no verify, so its claim is status `success`.

**Drift.** The gold is from 2026-10-20 captures, and the live pages have changed since then. A changed value scores as wrong for every arm alike. The drift is not isolated, the same as in K1. It is bounded in two ways:
- **The arms ran on the same day, interleaved per case,** so drift affects all three alike. The comparison between arms is the result. The absolute counts are not comparable with the frozen-capture numbers.
- **The gold marks 60 of the 294 required fields as other than `static`.** The table splits by that mark. List records marked `static` also move when new items come first, as K1 found.

All 42 cases stay in every denominator, including blocked, failed and changed pages.

## What the run shows

- **With the model fallback on, Octocrawl does not reach Firecrawl's field count overall:** 98 against 127 of 294.
- **The gap is in the 19 list/table cases.** There no model is called, and Octocrawl's selected lists hold 29 of 199 required fields correct, against Firecrawl's 56.
  - Firecrawl's lead there is V22, V23, V27 and V28: 45 of 48 fields, against Octocrawl's 15.
  - Both arms get 0 on V15–V17, V19, V21, V29, V32 and V35, as in K1. K1 traced most of these losses to list items that changed after 2026-10-20.
- **On the 23 cases without a selected list, Octocrawl + Haiku about equals Firecrawl:** 69 against 71 of 95 required fields, and more cases accepted (14 against 10), with 0 false successes against 13.
- **False successes: 5 of 42 for Octocrawl + Haiku, against 27 of 42 for Firecrawl.**
  - Octocrawl's 5 are the same as with the model off. Turning the model on added no false success, live.
  - The model arm claims success on 19 cases and 14 of them are accepted. Firecrawl claims success on 40, and 13 are accepted.
- **Cost:**
  - Octocrawl + Haiku: $0.0208 for the 19 model calls, from the API's usage. There was no other spend.
  - Firecrawl: 200 credits (1318 → 1118).
  - Octocrawl off: $0.
- **Against the frozen captures** (re-score after #697, [2026-10-23-f2-title-availability-frozen-328b981f.md](2026-10-23-f2-title-availability-frozen-328b981f.md)): off 125 and Haiku 169 of 294 frozen, against 60 and 98 live.
  - Which engines: frozen off ran on `328b981f`, whose `packages/` tree is this run's (`2a473793`). Frozen Haiku ran on `8cd34d30`, a commit before #697's review fixes. That record infers, but did not measure, that the two give the same result.
  - Where the fields were lost: 65 off and 71 with Haiku. 62 of them are in the 19 list/table cases. The rest are V40, which got `connection_error` in both arms, and, for Haiku, V39, which got `connection_error` too. (Off got Open Library's verification page on V39.)
  - Why is not established. Page drift probably explains most of the list losses, as in K1. But this run cannot separate drift from access differences.
- **Against K1's live windows:**
  - Firecrawl json: 118 and 121, now 127.
    - Against window 2: +6, from V24 (0 → 3), V20 (0 → 2) and V04 (0 → 1).
    - Against window 1: +9 net. Up on V27 (+6), V13 (+4), V10 (+3), V20 (+2), V04 and V38 (+1 each). Down on V22 (−3), V30 (−3) and V31 (−2).
  - Octocrawl off: 69 and 56, now 60.
  - The engine changed between those runs (#696, #697 and the D6 work since `b233d232`), and so did the pages. The two causes are not separated.

## What this does not measure

- **The driver after the run:** a review after the run found three defects in this PR's driver change. A missing key could corrupt a saved request. A cap that is not a number did not stop the Firecrawl arm. A resumed run did not count the spend of answers already saved. All three are fixed in a later commit of this PR. None of them affected this run: all keys were set, both caps were numbers, and the run was a single uninterrupted one (`run.log` ends `exit=0`, 42 answers per arm). The run's commit is `68ed82d4`.

- **Repetition:** one run per arm, so run-to-run variance is not measured, for the model or for the live pages.
- **Effort and models:** the default `low` effort only, and Haiku only. Sonnet was not run live.
- **The list path:** the model fallback is not called when an `itemSelector` is set, so this run says nothing about a model on the 19 list/table cases.
- **Drift:** it is not isolated, as stated above.
