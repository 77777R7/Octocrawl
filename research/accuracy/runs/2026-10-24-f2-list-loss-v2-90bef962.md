The frozen and live outputs agree on every field except V22's `latest_version`. So, apart from those three, the loss is extraction, not drift or access. Firecrawl lost the same three to drift.

**Why the keys were not mapped.** The json of a selected list is mapped from the list's records: a schema key is filled only from the list field of the same name (`docs/json-extraction.md`). In these four plans the list names only the cells a selector can tell apart. The selector notes in `list_selectors.v1.json` say why the others were left out: they are plain `td` cells with no attributes, and the first plain `td` is the key cell. Octocrawl's list selectors do not take `:nth-child` or sibling combinators (`SUPPORTED_SELECTORS`, `packages/extract-tf/src/selectors.ts`), so with today's engine no selector could name them. The frozen selectors are therefore not wrong for this engine, and no change to them is proposed.

**One selector observation, reported and not changed:** V27's `itemSelector` `table.standard > tbody > tr` also matches the four rows of the status-key table under the versions table, as its note says (7 items). The json therefore holds four empty records after the versions and stays `incomplete`, and its verify contract fails. The first three records, which the gold scores, are unaffected.

## Step 2: the change

**Engine gap:** the selected items are table rows, and the page labels each column with a header naming the key, but the json could not use the header. This is general (any table read through a list with a partial field list), deterministic and traceable, so it is fixed in the engine. Commit `90bef962` (branch `claude/f2-list-loss-v2`), rule in `docs/json-extraction.md`:

- When the items a list's `itemSelector` selects are rows of an HTML table with one header row, a record key no list field names is read from the row's column whose header names the key. Headers are compared as page labels are: exact first, then without a bracketed qualifier.
- The value is the text of the row's cells under that header, joined by a space when the header spans several (V27: `8 Dec 2022 3 years, 10 months ago`). The evidence names the column (`record 1 column 3 "First release" text`).
- Nothing is filled when:
  - a list field names the key: its own value is kept, null or not;
  - no header names the key: V22's `security_support_until` is not read from `Security Support`;
  - columns that name the key state different values: the key is left out with `field_ambiguous`;
  - the table has a cell spanning rows, or has no header row or several.
- The columns are read in the same parse as the list, and only when a json schema reads a list with an `itemSelector` (`FetchOptions.listColumns`). Their text is bounded by the list's character budget. A column counts against the selected-list JSON's 1,000,000-character budget only once a key is read from it. They are not part of the `list` format's output: `list` and its CSV are unchanged.
- `EXTRACTOR_VERSION` `extract-tf/43`.

**Tests**, each failing before the change (fixtures minimized from V22, V23, V27 and V28):
- `packages/extract-tf/test/list.test.ts`: columns of a selected row, a spanning header, a header row outside `<thead>`, and the cases that give no columns, plus the budget.
- `packages/api/test/listJson.test.ts`: mapping, evidence, a named field kept, a key no header names, a column with no text, columns that disagree, misaligned columns, and the JSON budget.
- `packages/bench/test/errorPage.test.ts`: the lane reads columns only when asked, and only for an explicit `itemSelector`.
- `packages/api/test/listJsonSubject.integration.test.ts`: end to end over HTTP, compact and debug. `list` is unchanged, and `listColumns` appears in no response.

## What is left, and a proposal not built

- **V22 `security_support_until` (3 fields):** the header is `Security Support` and the key adds `_until`. Matching a key to a header that is only part of it is not a rule this change makes: `Active Support` stands beside it, and a partial match would guess. The deterministic path leaves it out. A model would fill it.
- **Proposal, not built: run the model fallback on selected lists too.** Today a request with an `itemSelector` never calls the model (`docs/json-extraction.md`). It is a change of product behaviour, so it is only written up here.
  - **What it would change:** for keys that neither a list field nor a column fills, a selected list with `modelFallback: true` would call the model once per page with the selected records. Each value would be kept only where F2's check locates it inside that record's own item (the row), not elsewhere on the page.
  - **What it would need:** F2's row binding has no entry point today; F1/F2 (2026-10-20) noted that table and list-row binding could not be tested. It would need its own failing tests, and a per-record locator over the item's text instead of the page's Markdown.
  - **Risks:**
    - a model call, and its cost, on every list page where a key stays empty, up to the 2,000-record JSON bound;
    - a value located in a neighbouring row would be a wrong-record answer that a presence-only verify contract passes, the same pattern as the five false successes #696 and #697 removed;
    - longer prompts on large lists.
  - **What it would gain on these four cases:** at most 3 fields (V22), against the 27 the columns now give with no model.
- **Live effect not measured.** No live page, Firecrawl or model was called. The live answers of 2026-10-23 kept no source HTML, so they cannot be re-read with the candidate. That the 27 fields would also be filled live is inferred from the frozen run and from Octocrawl's identical per-field results frozen and live on these cases (except V22's drift). Whether the live pages still have the same header rows was not checked. It is not measured.
- **The rest of the list gap** in the live comparison (V15–V17, V19, V21, V29, V32, V35, 0 for both arms) was not part of this investigation. K1 traced most of it to list items that changed after 2026-10-20.
