## Setup

- **Services:** live hosted API `octocrawl-api` and worker `octocrawl-jobs` on `octopus-w2l-20260924-7r7`, asia-southeast1, through `https://api.octocrawl.dev` unless named. Octocrawl's own reads leave from Cloud Run directly, with no proxy.
- **Runner:** this Mac, through its local proxy (`HTTPS_PROXY`), with `NODE_USE_ENV_PROXY=1` for Node.
- **Key:** issued for Howard's account for this run (`scripts/hosted/issue-key.mjs`, digest `c2caa51c…`), HTTP lane only, so every request was pinned to `fastMode`. Revoked afterwards.
- **Global switch** `hostedConfig/jobs.enabled`: turned on for the run, and off again after it.
- **Credits:** the account had 878 credits. 2,000 purchased credits were added to it for the run, by a Firestore increment on `credits/{uid}.purchased`. It ended with grant 0 and purchased 1,279, so the run spent 1,599 credits.
- **Daily pool:** the worker's `W2L_JOBS_ACCOUNT_DAILY` was raised from 2,000 to 4,000 for V2, because of the pool bug D9 below. It was restored to 2,000 afterwards (revision `octocrawl-jobs-w5-d292501`).

## V1: the parity crawl and batch cases against hosted

Cases L02, L04, L11, A13–A15 and A26–A35 of [research/parity/sites.md](../parity/sites.md). Command:

```bash
W2L_API_URL=https://api.octocrawl.dev W2L_HOSTED_API_URL=https://api.octocrawl.dev W2L_API_TOKEN=<key> NODE_USE_ENV_PROXY=1 \
  node research/parity/run-sites.mjs --only L02,L04,L11,A13,A14,A15,A26,A27,A28,A29,A30,A31,A32,A33,A34,A35 --record <record>
```

The runner now sends `W2L_API_TOKEN` as a bearer token on REST calls. In round 2 it also waits through the hosted `queued` status.

| Round | Deployed code | Cases passing | Checks passing |
| --- | --- | --- | --- |
| 1 | API and worker 5141c6d6 | 2/16 | 35/90 |
| 2 | API 5141c6d6, worker 232e984d (D9, 4 GiB) | 7/16 | 73/90 |

**Round 1 is not a measure of hosted.** The runner took `queued` for a finished job and read before the job ran; that is why the later cases show 0 pages. It also started the cases back to back, which queued them behind each other. It surfaced three real problems:
- **D8:** the worker crashed with a JavaScript heap out of memory at 2 GiB.
- **D9:** the day's job pool counted 101 pages a slice whatever a job had left.
- **D10:** a 56 MB docs archive was read as a page; this was found from round 2's data.

**Round 2: 17 failed checks.** None is a wrong page:
- **The status has no `budgetExceeded`** (L02, A32). The hosted job status does not carry it.
- **No progress mid-run** (A14, A34). A small job runs as one slice, and the counts move only when a slice commits, so a poll during the slice sees 0.
- **No trace in hosted items** (A15 `crawlDelay`, A35 `hostSpacing`). The spacing itself held: A15's two fetches were 3,902 ms apart against robots.txt's 2,000 ms.
- **A29, keyless calls:** a call without a key is not refused. Hosted serves keyless scrapes on purpose, so the case's 401 expectation does not apply.
- **A14 and A31 page lists:** `/pages` answered 500 for limit 50 and 100. Cloud Run logged "Response size was too large", because one item was the 56 MB archive. Fixed in D10 (#614): after the fix the same job pages 24 items within the budget, with a cursor for the rest. The cases were not re-run after the fix.
- **A32:** the crawl of Wikipedia's Web crawler article stored 1 page where 7 were expected. Not investigated.
- **L11 `anyOf`:** observed `okokx | xxx`. Not investigated.

## V2: a 1,000-URL batch, read back from new instances

1,000 book pages of books.toscrape.com, collected from its 50 catalogue pages. Started on API revision `octocrawl-api-cap-d292501` and worker `octocrawl-jobs-w4-d292501`, both at main d292501e with main CI green.

**Run** (job `ed7a36c2-1257-42e3-ad92-95ff7ad85104`):
- completed in 307 s, in 10 slices of about 100 pages each, a slice every 20–40 s;
- 1,000 pages, 0 errors, 1,000 credits;
- results kept until 2026-10-26T19:07:50Z.

**Read-back.** A new no-traffic revision of the same image, `octocrawl-api-read-d292501` (tag `h29read`), was deployed only to read from. Its log shows one "Starting new instance". Reads through that tag and through api.octocrawl.dev gave the same answer:

| Read through | Item requests | Items | Unique URLs | Statuses | URL digest | Markdown characters | Export lines |
| --- | --- | --- | --- | --- | --- | --- | --- |
| h29read (new instance) | 10 | 1,000 | 1,000 | success 1,000 | `78efa314bf9795cc` | 4,266,368 | 1,000 |
| api.octocrawl.dev | 10 | 1,000 | 1,000 | success 1,000 | `78efa314bf9795cc` | 4,266,368 | 1,000 |

Every requested URL was among the items. The script first counted 1,006 export lines, with Python's `splitlines()`, which also breaks at Unicode line separators inside the Markdown. Split at `\n`, the export has 1,000 lines and no URL twice.

The plan said to scale both services to zero first. Instead, the read used a revision that had never served, which also guarantees a new instance.
