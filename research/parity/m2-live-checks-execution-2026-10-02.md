## Deviations from the plan, stated

- C, E-B and E-D answer `failed`/`empty_unverified` where the plan expected `success`: scrapethissite's gotcha page and badssl's pages hold one sentence or one heading, which W2L does not read as main content. The option under test did what it says in each case (the header reached the server; the certificate was not verified and the page came back). Whether a one-line page should be `success` belongs to the error model.
- F's `/js/` result keeps 254 chars of the page as evidence instead of the `markdown: null` the plan wrote; W2L keeps the whole page on every `empty_unverified` result.
- D: Wikipedia served the desktop article to the mobile identity on the http lane; no redirect to `en.m.wikipedia.org` was observed, so `finalUrl` is the requested URL.
- E-E ran on port 8789, not 8788.

## What the run also showed

- The browser rung's as-sent client hints: while testing this batch, Chromium was found to send its own `sec-ch-ua` (`"HeadlessChrome"`) on a server redirect hop and on a page's own requests, where a context's extra headers do not reach, and the compliance record repeated the declared value because Playwright reported the headers it had set rather than the wire's. `3e20c60` sets the declared identity as Chromium's user-agent metadata, so every request carries the declared hints (shown by `packages/bench/test/pageOptions.test.ts` on a redirect across two loopback origins); the live runs above were made with that change.
- The browser rung cannot withhold custom headers from a server redirect to another origin: Chromium follows the redirect with the request's headers and no route sees the hop. It records `custom_headers_forwarded` instead; the http rung withholds them (`custom_headers_withheld`). No live run redirected cross-origin; the lane difference is covered by the unit tests.
