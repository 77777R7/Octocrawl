## Deviations from the plan, stated

- The plan's requests name the API on 8787 and the receiver on 8799; this worktree's ports are 8827 for the API and 8828 for the receiver (8787 belongs to another session), and every request above went there. The raw outputs and this record are dated by the run (2026-10-02), not by the plan (2026-09-30); the re-audit record takes the next letter after `main`'s `reaudit-2026-10-02g.json`.
- The plan's check A expects five `page` events "each page carrying status/lane/markdown": one of the five pages of a 5-page crawl of quotes.toscrape.com is `/login`, which is `failed`/`empty_unverified` on both rungs (a login form with no main content; HTTP 200). Its event was delivered with that status and the form's Markdown as evidence, which is the contract (a page event for every outcome); the crawl's `/pages` route lists the four non-error pages and `/errors` the fifth, and the checkpoint's five step ids are the five `page.id` values exactly.
- A, B, C and D each crawl the same sandbox; the plan asked for four crawls and they were run as four crawls (15 pages), so quotes.toscrape.com was requested 26 times in all (18 http requests, the `/author/Albert-Einstein` redirect hop counted, and 8 browser-rung loads: `/login` four times, `/tag/change/page/1/` and `/tag/deep-thoughts/page/1/` twice each); books.toscrape.com 3 times. A real site of the frozen test set is not part of this batch's checks.
- The receiver is a scratch `node:http` script rather than `examples/webhook-receiver.ts`, which requires a signing secret and refuses an unsigned POST; the plan's checks send unsigned deliveries (no `secretEnv`), and the signed path is fixture-tested (`packages/api/test/jobWebhooks.test.ts`, `packages/runtime/test/delivery.test.ts`). Both scratch scripts lived under the session's scratchpad outside the repository and were deleted after the run.
- B's "receivedAt later than the first poll that saw `completed`" held with 79 ms to spare, within the plan's "or equal within the poll interval"; the delivery worker polls every 500 ms, so a delivery can precede or follow such a poll by up to that much. The order that is guaranteed, and observed, is terminal row (41.085Z) before delivery row (41.086Z) before the POST (41.280Z).
- The terminal payload's own `report.webhook` block shows the counts at the moment the report was built, before that event's own enqueue: A's `completed` body says `pending 1, delivered 5` (the fifth page's delivery was still in flight). The status routes read after the run say `pending 0`.

## Findings

1. Delivery cadence: each delivery was claimed 144 to 458 ms after it was enqueued (the API process's worker polls every 500 ms when idle) and answered within 6 ms by the loopback receiver; a crawl's page events therefore arrive about half a second after the page is stored, and `GET /v1/crawl/:id` can already report `webhook.pending 1` for a page event the receiver has not yet seen. Nothing to change; stated so a receiver's timing expectations are right.
2. A page event is sent for every persisted outcome: four of the five crawls here delivered a `failed`/`empty_unverified` event for `/login` with the login form's Markdown as evidence. A receiver that wants successes alone filters on `page.status`; `events` filters by event, not by page outcome.
3. The receiver never sees a header beyond the request's own, W2L's three identifiers and the transport's (`connection`, `content-length`, `content-type`, `host`): the `Authorization` and `X-Run` values of C and E were sent lower-cased and are stored in `section-b-control.sqlite` (`headers_json`) alone; no response of this run carries them.
4. `/tag/change/page/1/` and `/tag/deep-thoughts/page/1/` went to the browser rung after the http rung's thin answer (one `low_content_yield` warning kept on the http answer of `/tag/deep-thoughts/page/1/`), and `/author/Albert-Einstein` cost two http requests (a redirect to the trailing-slash URL); pre-existing lane behaviour, unchanged by a webhook, noted for the fetch count.
5. `GET /v1/batches/:id` now reports `succeeded` and `failed` beside `completed` (E: 3 / 0 / 3), the counts the extract-webhook contract names; a batch's `completed` keeps its meaning of items with a result.
6. Known leftovers, named here: the `/fc` shim's webhook mapping and Firecrawl-shaped payload, the hosted-mode refusals (`webhook.url must be https (...)`, `webhook.url must be a public address`), the `secretEnv` signature, the resume and restart reconciliation and the `cancelled` event are fixture-tested in `packages/api/test/jobWebhooks.test.ts` and not part of this run (no hosted API and no interrupted job here); a Monitor destination takes no `headers`, `metadata` or `events` yet (`events, headers, metadata and payloadFormat are job webhook options; a Monitor destination takes none`, for the M5 group); `GET /v1/batches/:id/events` still re-reads the report every 500 ms per client and the `JobEventHub` has no subscriber yet (the watcher batch); the `w2l` CLIs have no `--webhook` flag; `npm run delivery:worker` and the API's own worker may both run against one control database (leased claims); a job that runs again (a resumed crawl, a batch appended after completion) suffixes its later terminal event id with the attempt id.
