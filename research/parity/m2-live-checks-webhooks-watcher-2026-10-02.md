## Findings

1. Event cadence over the WebSocket: a crawl page's `document` frame reached the SDK 0 to 2 ms after the step's `createdAt` in the checkpoint (`watch-crawl.jsonl` against `steps-summary.json`, all 20 documents), and its `snapshot` followed 1 to 3 ms later, the report read right after the page. The first document of a books.toscrape.com crawl came 4.5 s after the 202 because the crawl reads `/sitemap.xml` (404 here) before its first page; the batch's first came at 663 ms. Nothing to change; stated so a client's timing expectations are right.
2. One report read per page per job held: the stream after each page reads the report once and fans it out, so the 21 snapshots of A cost 21 report reads for the one subscriber, where the audit's SSE re-read the whole batch report every 500 ms per client (12 s of A would have been 24 reads for one client and 48 for two). A second subscriber of the same job shares each read (`sharedReport` in `jobStream.ts`, keyed by the step id).
3. The polling transport's documents are the same rows: B's five documents and C's five (the same pages of the same sandbox, watched by polling and by WebSocket) carry the same URLs and statuses, with `/login` `failed` in both; the only difference between the two crawls is which rung's answer the ladder kept for `/tag/change/page/1/` and `/tag/deep-thoughts/page/1/` (B kept the http answer on two of them, C the browser's), the pre-existing lane behaviour the webhooks batch noted.
4. The watcher's `snapshot` count on the poll transport is one per poll round whose report changed (5 here, one per page, since `wallMs` moves): a client that wants fewer snapshots raises `pollIntervalMs`.
5. The `/status/404` scrape kept no page (`markdown null`), so the 404 hint took its no-page form, `the server answered 404; check the link`; the with-page form (`…; the markdown is that error page, not the requested page; check the link`) is the one `batch.test.ts` sees on the fixture's HTML 404.
6. Known leftovers, named here: a stream for a job paused by a shutdown stays open until the server closes (no terminal is emitted; the watcher then falls back or reconnects); `stream_overflow` (a client more than 10,000 events behind) is unit-level only; the hosted-mode WebSocket path (bearer header, the `w2l.token` subprotocol, the refused bare handshake) is fixture-tested in `jobStream.test.ts` with a real listener and `createApp({ tokens })`, not run against a hosted API here; the Firecrawl v1 shim adds no socket path (M4); MCP streams nothing (said in `wait_batch`'s description and the docs); the merged extract `data` / `sources` and link-following extraction wait for the M5 model client, which is why D and E are re-audited `weak`; `creditsUsed` and `expiresAt` stay `null` on the shim; the `w2l` CLIs have no watch command.
