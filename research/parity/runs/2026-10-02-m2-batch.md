## Findings

1. The idempotency index outlives the API process (D4): the key the 21:03 run recorded from `packages/api/dist/cli.js` replayed its batch `c7975ba3-…` from this instance started with `--import tsx` 47 minutes later, with `replayed: true` and no fetch. The 21:03 record's phrase "per task root and per API process" and the docs' "kept by the one API process that runs that task root … not a lock between processes" (docs/batch-scrape.md, README) are about ownership: one process runs a task root at a time. The rows themselves are durable (`<task root>/idempotency.sqlite`, 24 h expiry, as the docs also say), so a retried submission is answered from them after a restart; nothing to change, stated here so "per process" is not read as "lost on restart".
2. On a batch run again by an append (E3), `GET /v1/batches/:id` mixes two scopes: `requested`, `completed` and `remaining` span every attempt (12, 12, 0) while `pagesFetched`, `wallMs` and `attemptId` are the latest attempt's (2, 3,670, `9766de4e-…`), as the report has always been the latest attempt's `CrawlReport` with the batch's totals beside it.
