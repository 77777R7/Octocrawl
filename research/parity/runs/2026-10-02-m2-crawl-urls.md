## Deviations from the plan, stated

- B1 reports `collapsed 6`, not 24: the `?per_page=100` page carries six `page_num` links (the plan's 24 is the 25-row page's pagination). Every one of the six merges is named in the samples.
- A1, B2, D1, G1 and G4 recorded pages fetched by two workers in the order they finished, not in the page's or the sitemap's order; the sets are the plan's.
- E1's two asset pages were a PDF and an XLSX, the first two asset links in document order; the `.ods` the plan mentions was enqueued and not fetched within `maxPages 3`.
- The plan's sitemap bodies used Firecrawl's `scrapeOptions.includeLinks`; the native request takes `includeLinks` at the top level, which is what was sent.
- G1's `budgetExceeded` is null although 10 pages met `maxPages 10`: the load collected 10 entries, one of them the seed, so the frontier drained with nothing refused.
- G2's include evidence is sitemaps.org's own (its homepage links `.php`, its sitemap `.html`); G4 was not needed as the fallback the plan allowed for.

## Findings

1. A crawl escalates per page as a scrape does: on quotes.toscrape.com the one-quote tag pages (`/tag/<tag>/page/1/`, 537 chars) end the http rung with `quality_low_yield` and are fetched again on `browser_local`, so a 20-page crawl of that host cost 28 page loads plus the browser rung's own robots.txt read (each rung keeps its own cache, as the execution record of the same day found). Pre-existing ladder behaviour, surfaced here because a crawl check happened to reach those pages; the batch record of the same crawl body reported every page on the http lane, so which pages a 20-page crawl of that host reaches, and whether any escalates, varies with the frontier's order. The option under test (the active list) was unaffected.
2. The sitemap reader's robots.txt read is not observable in the saved outputs: on www.sitemaps.org (G1) and webscraper.io (G4) every page's `usage.timings.robotsMs` is below 0.1 ms, because the reader shares the lane's cache and read robots.txt before the first page. The one read per host there is inferred from the design, not seen; a robots.txt read marker on the report (a follow-up the batch named) would make it observable. On www.gov.uk, G3's reader found the robots.txt E1 had read (G3's seed `robotsMs` 0.03 ms), the one cache per process at work.
3. In `sitemap: "only"` no page carries a `links_offered` event (G1: none of the 10 pages), while the README describes the event as being on each page's trace; the review of the sitemap batch flagged the sentence, and the live run shows the gap.
4. The independent reads of the sitemap files have the same sha256 as W2L's file records (www.sitemaps.org `5be36d03...`; webscraper.io `f1e05e24...` and `69fbc766...`), so the bytes W2L hashed are the bytes the sites serve to another client through the same proxy. W2L still saves no sitemap body; the hash is its only record of them.
5. C2's duplicate step is now backed by its saved trace (the listing was read with `includeDuplicates=true&debug=true`): the `duplicate_content` event, the `egress_proxy` event and `evidence.envProxy` are in the raw output, which the URL-scope batch's record could not show.
6. H1's `crawl_delay` events record `requiredDelayMs 250` (the origin scheduler's minimum interval) and `robotsCrawlDelayMs null`: with `maxConcurrency 1` the pages followed one another with gaps of 0 to 1 ms after the seed's 3,170 ms gap, so the sequencing, not the interval, bounded the crawl; the interval is enforced between request starts, which were already more than 250 ms apart.
