## Findings

1. `blockAds` does not govern the whole-page path (E4, E5). With `onlyMainContent: false` the `markdown` and `html` keep the `advertisement` container, and the Markdown even carries the aborted ad pixel's `![]()` reference, with the default as with `blockAds: false`: `wholePageMarkdown` (`packages/bench/src/subjects/errorPage.ts`) is `htmlToMarkdown` of the raw body and `wholePageBody` (`packages/extract-tf/src/prune.ts`) strips never-shown elements only; neither runs the token pruning, which was always main-content only. The network side (`ads_blocked`, count 2 on E4) is unaffected. README's `blockAds` bullet ("before extraction on every rung"; `false` "keeps ads and cookie banners in `markdown` and `html`") and the contract of `scrape-formats.block-ads` ("ads and cookie banners absent from markdown, html") do not name the exception. Pre-existing; either the switch reaches that path or the docs name it. Recorded in the status CSV as `weak` for `scrape-formats.block-ads`.
2. Each rung holds its own `RobotsOriginCache` (`packages/bench/src/subjects/resilientHttp.ts:73`, `browserLocal.ts:278`): a scrape that escalates fetches robots.txt twice, once per rung (the fixture log shows two requests per instance, one with each rung's User-Agent; A3's and C2's browser-rung records say `skippedFetch: false`). The header comment of `packages/bench/src/robotsLookup.ts` ("shared by the HTTP and browser arms") describes an older arrangement. This sets the robots.txt counts below.
3. The browser rung declares the installed Chromium's major, 151, in its User-Agent, its client hints and the signed `sentHeaders` (`browserLocal.ts`: "Real Chromium major, not the floor constant"), while the http rung declares the floor, 128 (`CHROME_MAJOR_FLOOR`). Each identity is coherent with its own hints, and the honesty check passed on every browser-rung fetch of this run (no `identity_mismatch` in any raw output); the two rungs of one scrape still present two Chrome versions to the same host. Pre-existing, by design; noted for the owner.
4. The browser rung's withholding of custom headers from a redirect hop to another origin (`276e35b`, `custom_headers_withheld`) was not exercised live: no check redirected across origins, and no `custom_headers_forwarded` appears in any raw output; `packages/bench/test/pageOptions.test.ts` is the evidence for that path.
5. The browser rung's signed compliance record lists a custom header verbatim in `sentHeaders` (A3's `accept`), beside `accept-language: en-US` from the context locale: anything put in `headers` is on the record, as README says.
