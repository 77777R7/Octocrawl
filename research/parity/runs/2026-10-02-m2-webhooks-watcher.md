## Findings

1. The poll transport does not deliver every page in the compact shape the stream transports do (P1): the four kept pages came as the `/pages` route's compact rows (`trace: []`, no `audit`), the failed `/login` came as the `/errors` route's row with its full `trace` (10 events) and `audit`. `packages/sdk/src/watcher.ts` drains `getCrawlErrors` unstripped, while the SSE and WebSocket frames (W1, W2, S1, S2) and the `/pages` listing strip both; the watcher's own header ("every transport delivers the same compact pages the items routes list") and the README's watcher paragraph promise the same shape on every transport. Nothing is missing or doubled (the page arrived once, with its status), so the check passes; the shape should be made the same (strip `trace` and `audit` from the errors rows on the poll transport) and this is the one behaviour of the group this run found at odds with its documentation.
2. Delivery cadence: each of the 22 deliveries was marked delivered 2 to 473 ms after it was enqueued (the API process's worker polls every 500 ms when idle) and the loopback receiver answered within a few ms, so a page event arrives up to half a second after its step is stored and `GET /v1/crawl/:id` can report `webhook.pending 1` for an event the receiver has not yet seen. A receiver can also learn of completion before a poller does: B's `completed` POST reached the receiver 2 ms before the first poll that saw `completed` was sent. The order that is guaranteed held every time: terminal task row, then the delivery row, then the POST.
3. The terminal payload's own `report.webhook` block counts the deliveries before that event's enqueue: A `pending 1, delivered 5`, C `pending 1, delivered 3`, D `pending 1, delivered 2`, E `pending 1, delivered 3`, B `pending 0, delivered 0` (its one event is the terminal). The status routes read after the run say `pending 0`. Stated so a receiver does not read the block as the final tally.
4. Stream cadence over the WebSocket: a document reached the SDK 0 to 2 ms after the step's `createdAt` (all 40 documents of W1 and W2) and its snapshot 1 to 4 ms later (the report read once per page and fanned out). A crawl's first document comes after its `/sitemap.xml` read (2,903 ms in W1, 404 here), a batch's after its first fetch (1,714 ms in W2).
5. The hint text of H1 asserts an expectation about the host ("expect other pages of www.bls.gov to need the browser lane too") that W2L did not check: no per-host lane memory exists, and each page of a crawl starts on the http rung. The recorded facts in the sentence (the http lane's 403 / `bot_detected_generic`, the local browser lane served the page) are the ones the ladder summary holds; the "expect" clause is a prediction. Also on this row: the one scrape cost two page requests and two robots.txt reads (one per rung), the pre-existing ladder behaviour the execution and batch records noted.
6. `/author/Albert-Einstein` costs two http requests (a redirect to the trailing-slash URL, `requestCount 2`) and each `/tag` page and `/login` two (http then browser) in every 5-page quotes.toscrape.com crawl, so such a crawl makes 9 page requests for 5 steps; pre-existing lane behaviour, unchanged by a webhook or a stream, noted for the fetch count.
7. Known leftovers, named in the batches' records and not exercised here: a stream for a job paused by a shutdown stays open until the server closes; `stream_overflow` is unit-level only; the hosted WebSocket path is fixture-tested, not run against a hosted API; MCP streams nothing and the frozen v1 shim adds no socket path; the `w2l` CLIs have no `--webhook` flag or watch command; `creditsUsed` and `expiresAt` stay `null` on the shim; a Monitor destination takes no `events`, `headers` or `metadata` yet (M5); a job run again suffixes its later terminal event id with the attempt id, and a resumed crawl without `useCached` refetches its pages as new steps, each a new `page` event; `succeeded + failed` counts every step of every attempt while `completed` counts distinct URLs, so they diverge once a URL has steps in two attempts (no run here produced that case); the merged extract `data` / `sources` and link-following extraction wait for the M5 model client, which is why X and U are `weak`.
