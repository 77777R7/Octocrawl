# Live checks 2026-10-03: saved logins from the user's Chrome (interaction group I1)

Source commits: steps 1 to 8 on `5d29898`, step 9 on `422aa8b` (branch `claude/i1-login-session` on `main` at `bb2d997`), run from source as `npx tsx packages/cli/src/cli.ts` (`w2l` below).
Network: proxied. HTTPS_PROXY=http://127.0.0.1:7890; the browser rung's trace records `egress_proxy` 127.0.0.1:7890. The Chrome connection is to loopback and goes direct.
Chrome: Google Chrome 154.0.8037.93 on macOS, the user's everyday browser (default profile), with "Allow remote debugging for this browser instance" already on; the user clicked Allow in Chrome's dialog for each connection.
Saved logins: a scratch file (`W2L_SESSIONS_FILE`), deleted after the run. Task root: a scratch directory (`W2L_TASK_ROOT`).
Sites: two public demo sites made for scraping practice. The user signed in to each in Chrome themselves; W2L entered no credentials.

Result: the import and mode `authed` worked end to end on quotes.toscrape.com (scrape and batch). On the-internet.herokuapp.com the import worked but the site did not accept the saved login (cause not known); on `5d29898` that was reported as `success` with the login page's text, and after the fix in `422aa8b` it is `blocked` / `login_wall` with a hint to import the login again. Mode `authed` on crawl was refused as intended.

Three runs before it with the default timeout ended `failed` / `timeout`: the authed browser's `page.goto` passed its 20 s navigation limit (`navigate_failed`), while the plain browser rung (`--wait-for 1`) and curl with the same cookies answered within seconds at the same time. Why that navigation was slow is not known. In the same minutes `w2l scrape https://quotes.toscrape.com/ --mode authed` was again `success` with the `/logout` link. |

Step 8, what was checked:
- The same `rack.session` value sent with curl to `/secure` was answered 302 to `/login` with a Chrome 154 User-Agent, a Chrome 151 one, and eight combinations of Chrome-like `Accept-Encoding` and `Accept-Language`. So the refusal is not explained by the User-Agent or those headers alone.
- Not checked: whether the user's Chrome tab was still signed in at the time of step 8, and whether the site keeps its session server-side. The cause stays unknown. On `5d29898` the redirect to the login page was not classified as `login_wall`, so W2L reported `success` with the login page's text; `422aa8b` fixes that (step 9).

Before the steps above, three imports found no cookie for the site and were refused with the message that now names the default profile and a normal window: the user had first signed in inside another browser (the Claude desktop app's built-in browser, which shares no cookies with Chrome), then once more before the quotes.toscrape.com sign-in had completed. These show the refusal path, not a product failure.

What this does not show:
- Unit and integration tests cover the rest and fail without their fixes: the authed rung first and a `login_wall` ending the run (`packages/bench/test/ladder.test.ts`), the engine reading the file read-only and never on a hosted engine, a crawl never carrying a login, the loopback-only guard (`packages/api/test/savedLogins.test.ts`), a re-imported login used at once in real Chromium (`packages/bench/test/authedSession.integration.test.ts`), the import's cookie selection, public suffixes and file mode (`packages/api/test/chromeLogin.test.ts`), the command line (`packages/cli/test/login.test.ts`).
- Not run live: the API server and the local MCP service in mode `authed`, Windows and Linux, a site that sets `__Host-` or `__Secure-` cookies, a login kept in `localStorage`, and an expired login.
